# T8 — questions and the fail-closed choices made

The audit log writer for holds, reviews and sends is I1's (not merged when T8 was built), so
T8 reads the record shapes from SPEC §5.8 / §5.9, the I1 card and T6's `parentIds`. Each choice
below picks the reading under which the auditor never vouches for something the log does not
show.

1. **A send forwarded with no approval on record.** The card lists "a signature with no linked
   approved `tx_review`" as UNVERIFIED, giving a tool result from a server that never showed
   Gate its transaction as the example. For `rpc_send_forwarded` the log is Gate's own record
   that it broadcast without approval, which is what I2 says can never happen.
   *Choice:* `tool_result` without a link → UNVERIFIED. `rpc_send_forwarded` without one →
   **FAIL**, even with no RPC. A config with `tx.approval: "never"` (tests only) therefore
   FAILs the audit.

2. **How `hold_approved` leads to `tx_review`.** The SPEC says to go "through `sendId` /
   `callId`" but names no field that ties a hold to one review. *Choice:*
   - The hold's parent is its `sendId`, or else its `callId`.
   - Only reviews under that parent count, and only if they have `verdict: "hold"` and come
     before the approval.
   - If `hold_approved` or `hold_created` states a `messageSha256`, that hash must match one of
     those reviews.
   - Otherwise the parent must have exactly one held message. Two or more is ambiguous, so the
     row FAILs.
   - Hold records that disagree with each other → FAIL.
   - **Ask to I1:** put `messageSha256` on `hold_created` / `hold_approved` so the link is
     exact.

3. **Which ids link a record.** *Choice:* `callId`, `sendId`, and every entry of a `parentIds`
   array (T6 holds carry it). A checkpoint hold with `parentIds: [callId]` also backs that
   call's tool result. The hash still comes from the hold's own parent (item 2).

4. **Order (I6).** *Choice:* only approvals logged before the send or result count, and only
   reviews logged before the approval. An approval logged after the forward → FAIL.

5. **Several approvals for one signature.** *Choice:* every `rpc_send_forwarded` of that
   signature must have its own approval. The landed message hash must be in the set approved
   for every one of those sends. For tool results, a later call that only mentions the
   signature (a status lookup) has no link and is ignored, but a broken link FAILs.

6. **RPC errors.** *Choice:* a failed or timed-out `getTransaction` → FAIL, as in document mode.
   Not found at the commitment → FAIL. Missing `meta` → FAIL (success cannot be shown).

7. **What the RPC returns.** *Choice:* only `encoding: "base64"` bytes are trusted. They must
   decode with `src/solana/tx.mjs`, and the first signature must equal the one we asked for.
   An RPC that answers with a different transaction → FAIL.

8. **Malformed signatures.** *Choice:* `rpc_send_forwarded` is derived by Gate from the bytes it
   sent, so a malformed or missing one → FAIL. A `tool_result` signature is pattern-extracted
   from free text, so one that does not decode to 64 bytes → UNVERIFIED.

9. **A broken chain.** *Choice:* the chain row FAILs at the first bad line. Only records before
   that line are read. Later records get one UNVERIFIED row ("not evidence").

10. **`--rpc-env`.** *Choice:* the default (`SFGATE_UPSTREAM_RPC_URL`) unset → chain only, as
    the card says. An explicit `--rpc-env NAME` that is unset → exit 2, because the user asked
    for a ledger check that cannot happen. A value that is not an env var name (someone pasted
    the URL) → exit 2, and the value is never echoed (I4).

11. **Default commitment.** *Choice:* `finalized`, same as document mode. `--commitment` accepts
    only `confirmed` or `finalized`.

12. **CRLF.** A `docs/proof/*.jsonl` checked out on Windows with `core.autocrlf` has `\r\n`
    line endings. The hash never covers the terminator, and canonical JSON cannot hold a raw CR.
    *Choice:* `\r\n` is read as `\n` and the output says so. Any other CR still fails the chain.
    **Ask to T9 / human:** add `*.jsonl -text` to `.gitattributes` so proof logs keep their
    exact bytes.

13. **Empty file.** Gate always writes `gate_start` first. *Choice:* an empty file → exit 2
    ("nothing to verify"), not a PASS over zero records.

14. **A forward the upstream rejected** (e.g. blockhash expired). The log still says
    `rpc_send_forwarded`, and the transaction is not on chain. *Choice:* FAIL ("not found"), as
    the card says for missing transactions.

15. **Not checked: the approver's signature.** `hold_approved` carries `publicKey` and the
    base58 approval signature, but not the approval message. So T8 cannot check offline that the
    approver key signed this exact hash. The chain has no external anchor either: anyone can
    write a self-consistent log. *Follow-up for I1/T8:* log `approvalMessage` (or its six
    fields) on `hold_created`. `audit --log` could then run `verifyApproval` against the
    configured approver.
