# T5 — open questions (RPC checkpoint)

Each entry: the ambiguity, the fail-closed reading implemented, and where it lives.
All of them are in `src/gate/rpc-checkpoint.mjs` and pinned by `test/gate-rpc-checkpoint.test.mjs`.

## Q1. `onSend` returns `code: number` — whose code is the JSON-RPC error?

SPEC §5.7 lets `onSend` return `{ forward: false, code: number, message, data }`; the card and
the acceptance list say a refusal is `{ code: -32099, message: 'SolFrontier Gate: ' + message, data }`.

**Chosen:** the JSON-RPC error code is always `-32099`; `onSend`'s `code` is ignored. A refusal
is then recognisable by its code alone, whatever the pipeline returns. The stable refusal reason
(`approval_rejected`, `unsolicited_send`, …) belongs in `data`. If I1 wants the pipeline's code
used, it is a one-line change in `answerSend`.

## Q2. "All other methods ⇒ forwarded verbatim" vs I1 "no RPC write method but sendTransaction"

The card forwards everything not in `deniedMethods` (default `['sendBundle']`). I1 refuses any
RPC write method other than `sendTransaction`.

**Chosen:** besides `deniedMethods`, any method matching `/^\s*send/i` other than exactly
`sendTransaction` is refused with `-32098` (`SendTransaction`, `sendtransaction`,
`sendRawTransaction`, a provider's `sendBundle` spelling). No standard Solana read method starts
with "send". `requestAirdrop` is still forwarded (it cannot move the user's funds); I1 can add it to
`deniedMethods`.

## Q3. `encoding: "binary"`

The Solana RPC accepts `binary` as a deprecated alias for base58. The card names only `base64`
and `base58`.

**Chosen:** anything but exactly `base58` / `base64` (including `binary`, `json`, `Base64`) is
`-32602`, never forwarded. Same for a base64 string that does not round-trip (unpadded, URL-safe
alphabet, junk characters Node's decoder would skip): the bytes `onSend` reviews must be the
bytes the upstream decodes. A transaction string over 4096 characters is also `-32602` (today's
maximum is 1683 base58 characters; the cap keeps a 2 MB string out of the quadratic base58 decoder).

## Q4. The client hangs up while `onSend` is still deciding

I7 lists "cancelled request → refuse". The audit log must not record a forward that never
happened (I6: the pipeline logs, then answers).

**Chosen:** `onSend`'s `meta` carries an extra `signal` (AbortSignal) that aborts when the HTTP
client disconnects or the checkpoint closes, so the pipeline can cancel the hold. The checkpoint
itself forwards **iff** `onSend` resolved to exactly `{ forward: true }`: one decision-maker, so
the audit log and the wire agree. If the client is already gone before `onSend` is called, `onSend`
is not called and nothing is forwarded. After `close()`, nothing is forwarded even if `onSend`
later says forward.

## Q5. "Verbatim" for the request that goes upstream

**Chosen:** the upstream receives `JSON.stringify` of the parsed request, restricted to the
JSON-RPC members (`jsonrpc`, `id`, `method`, `params`) in the client's order, never the raw bytes.
Raw forwarding allows a parser differential (`{"method":"sendTransaction",…,"method":"getBalance"}`
is a read to `JSON.parse`, last key wins; it is a send to a parser where the first key wins).
For the canonical JSON that client libraries emit, the bytes are identical (the acceptance test
asserts byte equality). Cost: a numeric id beyond 2^53 loses precision. Responses from upstream
are returned byte for byte (redacted only if they echo the upstream URL).

## Q6. JSON-RPC notifications (no `id`)

**Chosen:** answered like any request, with `id: null`, rather than silently dropped; a
`sendTransaction` notification still goes through `onSend`.
