# T4 — questions and the fail-closed choices made

Each entry: the ambiguity, the reading implemented, where it lives. None of them blocked the card;
the human can overturn any of them. Code: `src/gate/review.mjs`, `src/gate/tx-policy.mjs`; tests:
`test/gate-review.test.mjs`.

1. **Which instructions are "destinations"?** SPEC §5.5 names System `transfer` and SPL `transfer` /
   `transferChecked`. T3 questions #6 notes that `transferWithSeed` and `withdrawNonceAccount` also
   move lamports to `destination`, and SPL `closeAccount` sends the closed account's lamports to
   its `destination`. *Choice:* all six are checked. Leaving any out would be a way around the rule.

2. **Does a list entry cover the owner's token accounts?** SPEC: a destination is allowed if it is the
   wallet, a token account the wallet owns after simulation, *in `destinations`*, or the list is
   `"any"`. A `transferChecked` to a token account owned by an allowlisted address is not the
   address itself. *Choice:* refused (`destination_not_allowed`); the list names destinations, not
   owners. To pay an allowlisted person in tokens, list their token account. Pinned by a test.

3. **Delegation "on any account owned by the wallet".** Statically (no RPC) you cannot tell whose
   account an `approve` / `approveChecked` / `setAuthority` touches: a multisig or PDA authority hides
   it. *Choice:* when `denyTokenDelegation` is true, **every** top-level instance is refused,
   whatever its authority. `revoke` is not refused, because it only removes power.

4. **`maxOutflow.SOL` missing.** Every transaction pays a fee, so without a SOL cap every review
   would either deny or have no bound. *Choice:* `compileTxPolicy` throws `UsageError` (exit 2).
   `maxOutflow[So111…112]` (wrapped SOL) is also refused at load time, because wrapped SOL is folded
   into `"SOL"` (SPEC §5.5 step 4), so a separate cap would never be consulted.

5. **Unknown mint decimals.** The card says raw units and a warning. The warning needs a code, and
   none of the stable refusal codes fits. *Choice:* warning code `mint_decimals_unknown` (warnings
   only, never a refusal). For the cap comparison the mint is treated as having **0 decimals**,
   the smallest raw bound the configured cap could mean.

6. **Caps written as JSON numbers.** `maxOutflow` values are UI-unit JSON numbers in the examples.
   *Choice:* numbers are converted once through their shortest round-trip text (`0.05` → `"0.05"`,
   `1e-7` → `"0.0000001"`), and all later math is BigInt. Decimal strings (`"0.05"`) are also
   accepted; exponent strings, signs, `NaN`, `Infinity` and negatives are refused. Limit: a number
   literal with more than 15 significant digits is rounded by `JSON.parse` before Gate sees it. Write
   such a cap as a string.

7. **ALT fetch fails because of the RPC, not the table.** SPEC step 1 says "Decode (and
   ALT-resolve). Failure → `tx_decode_failed`". *Choice:* any step-1 failure, including an RPC error
   while fetching lookup tables, is `tx_decode_failed`. Either way the verdict is deny.

8. **Simulation preconditions that are not RPC failures** (`too many accounts to watch`, a malformed
   RPC response). *Choice:* reported as `rpc_unavailable` with the reason in `message`; deny.

9. **Extra watched accounts.** Besides decoded destinations, the accounts created by ATA
   `create` / `createIdempotent` and the target of `syncNative` are passed to `simulateWithDeltas` as
   `watch`. Their post-state is then known, so a wrapped-SOL ATA created in the same transaction counts
   as the wallet's own and its balance offsets the SOL outflow. The cost is a few more of the 40
   watch slots.

10. **What `summaryLine` shows.** *Choice:* exact amounts, never rounded (SPEC: "exact decimal
    strings"; the card's `−0.0010 SOL` example is read as illustrative). `−` is U+2212 and `…` is
    U+2026, as in the SPEC example. Programs are shortened to 4 chars + `…`. Mints other than USDC are
    shortened to the first 4 + `…` + the last 4 chars, so a ground `USDC…` vanity mint cannot read as
    `USDC`. When there are no amounts, a note stands in: `undecodable transaction (N bytes)`,
    `not simulated`, `simulation failed` or `no balance change`.

11. **`messageSha256` when decoding fails.** There is no message to hash. *Choice:* `null` (not a hash
    of the raw bytes, which would look like a message hash and be wrong). Such reviews are always
    deny, so no hold or approval message is ever built from them.

12. **`cluster` argument.** It is accepted, but review does not depend on it. The USDC symbol is
    mapped by exact mint address on every cluster.
